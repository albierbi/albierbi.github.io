Zero-Day Morning

A daily cybersecurity briefing that writes itself. One topic every morning, a breach, a CVE, a CTF technique, generated by AI and served from Redis. Here's how it's built.

Why

I wanted to learn something new in cybersecurity every day without having to go find and read an article myself each morning. The obvious fix was to make something generate it for me. And once it generates for me, it may as well generate for anyone who wants it.

It was also my first project that wasn't a tutorial or a clone, something I'd actually use daily. Building something meant to run unattended forces decisions a throwaway script never does.

Stack

Node.jsBackend runtime
VercelHosting, serverless functions plus a static frontend
Upstash RedisStores today's brief and the archive index
Anthropic APIGenerates the brief (claude-sonnet)
Vercel CronFires the generator once a day at 6am UTC

No framework on the frontend, just plain HTML, CSS, and vanilla JS. No database beyond Redis. The whole backend is four serverless functions.

Architecture

The main decision was to separate generation from serving. The generator runs once a day and writes to Redis. Every visitor reads from Redis. Nobody is waiting on an API call when they load the page.

flow
Vercel Cron (6am UTC)
    |
    v
/api/generate  --POST-->  Anthropic API
    |
    v  JSON brief
Upstash Redis  (brief:current, brief:YYYY-MM-DD, brief:index)
    |
    v
/api/brief  --GET-->  frontend
    |
    v
Browser renders the brief

Backend

Four serverless functions live in /api/:

brief.jsGET, reads today's brief from Redis and returns it
generate.jsGET/POST, calls Anthropic, saves to Redis, updates the archive index
archive.jsGET, returns the list of all past briefs (titles, dates, categories)
brief-by-date.jsGET, returns a specific past brief by YYYY-MM-DD date

Vercel auto-discovers files in /api/ and deploys each one as a serverless function. No Express server, no configuration needed for routing.

Storage

Redis holds three types of keys:

redis keys
brief:current          -> today's full brief JSON
brief:2026-05-05       -> that day's full brief JSON
brief:index            -> array of {date, title, category, difficulty}
brief:last-generated   -> ISO timestamp of last generation

The index key powers the archive page. It only stores metadata, so loading the archive doesn't pull down megabytes of HTML body content for every past brief.

I went with Upstash instead of a full database because of its free tier, its REST API (no persistent connection needed in a serverless environment), and Vercel's built-in integration for it.

Cron job

Vercel's cron feature sends an HTTP GET to a given path on a schedule. The config lives in vercel.json:

vercel.json
{
  "crons": [
    {
      "path": "/api/generate",
      "schedule": "0 6 * * *"
    }
  ]
}

The endpoint accepts both GET (from the cron) and POST (manual trigger). A rate limit key in Redis blocks generation if the last run was less than 20 hours ago. That stops a rogue cron from double billing on the Anthropic API, and stops anyone who finds the URL from spamming it.

Cron auth problem

Vercel crons send GET requests with no custom headers. My first version required a secret header, which the cron simply couldn't send, so it kept failing silently. The fix was to allow GET requests from the cron path without auth, and require POST plus a secret for manual triggers. The rate limit is the actual protection here, since triggering it costs about $0.05 and caps at once per 20 hours.

The prompt

The system prompt tells the model to write like someone who actually knows the topic, short sentences, concrete examples, no filler phrases. It asks for a JSON response with specific fields: title, subtitle, body HTML, TL;DR bullets, key terms, and resources.

A few rules I put in explicitly:

  • No em dashes
  • No phrases like "in the realm of", "it is worth noting", "in today's digital landscape"
  • Don't summarize what you're about to say before saying it
  • End when the content ends, no motivational wrap-up paragraph

The model returns JSON with the article body as an HTML string, and the frontend just renders it directly into the page.

Frontend

Plain HTML and CSS, no framework, no build step. The page fetches /api/brief on load, parses the JSON, and renders the article. If a ?date= query param is present, it fetches that date's brief from /api/brief-by-date instead.

Vercel serves the static files out of /frontend/, with rewrites in vercel.json pointing / and /archive.html to the right files.

Archive

Every time a brief generates, it saves the full content under a date key and pushes a metadata entry to brief:index. The archive page loads that index and renders cards, title, date, category, difficulty. Clicking a card loads that date's full brief through ?date=.

The filters on the archive page, difficulty, sort order, keyword search, all run client-side against the fetched index array. No extra API calls for filtering.

Problems along the way

Wrong model name

The first version used claude-sonnet-4-20250514 as the model string, which returned a 404 from the API. The correct string turned out to be claude-sonnet-4-5.

Redis returning objects instead of strings

Upstash's JS client sometimes hands back already parsed objects instead of raw JSON strings, depending on how the value was stored. I added a guard everywhere data comes back from Redis:

javascript
const brief = typeof data === 'string' ? JSON.parse(data) : data;

Vercel routing

Getting Vercel to serve the frontend from /frontend/ while the API functions live in /api/ needed explicit rewrites. Without them, Vercel tried to serve index.js as a plain static file instead of running it as a function.

Archive index parse crash

If parsing the archive index failed, it threw inside the same try/catch as the brief generation, so the whole request came back as "generation failed" even though the brief itself had already saved correctly. I wrapped the archive update in its own try/catch so a bad index can never kill a successful generation.

Where I used AI

I built this whole project through a chat with Claude, going back and forth on decisions, pasting error messages, and fixing things step by step as they broke. A lot of the actual code, the API routes, the Redis logic, the cron config, the CSS, came out of that conversation rather than me writing every line from scratch.

What was mine: deciding to build this in the first place, picking the stack, debugging live production issues by reading error logs and describing what I saw, deciding to switch to Upstash Redis when the JSON file approach didn't work on serverless, and deciding to separate generation from serving once I understood why that mattered for cost. The system prompt for the daily brief is also mine, including the writing style rules.

Takeaways

What I learned
  • Serverless functions on Vercel are simple to deploy but the routing config takes real effort to get right.
  • Decoupling generation from serving, write once to Redis, read many times, is the right pattern for anything with an expensive external API call.
  • Rate limiting off a Redis timestamp is simpler than trying to authenticate a cron job properly.
  • Prompting for JSON output works reliably if you're explicit about the schema and strip markdown fences before parsing.
  • The archive was an afterthought. Next time I'd design storage with history in mind from day one.
