Honeypot on a Public VPS

I put a fake SSH server on the open internet and logged everything for 75 days. Here's what showed up, and how the stack was built.

Why

I wanted to see what actually happens when you expose a server to the internet with nothing protecting it. Not theory, real traffic. So I got a cheap VPS, put a fake SSH server on it, logged everything, and waited.

I also wanted something in my portfolio that wasn't another CTF writeup. A dashboard full of real attack data against a box I set up myself felt like a better way to show I understand this stuff, not just that I can follow a walkthrough.

Stack

CowrieMedium-interaction SSH honeypot. Fakes a shell, logs every command typed
Python / FastAPICustom HTTP honeypot on port 80, logs all requests and headers
PromtailShips JSON logs from both honeypots to Loki
LokiLog aggregation and storage
GrafanaDashboards: attack map, timelines, top usernames, commands
Docker ComposeRuns the whole stack on a single $6/mo droplet

VPS specs: 1 GB RAM, 1 vCPU, Ubuntu 22.04. That's the smallest DigitalOcean droplet that can run this without constantly getting OOM-killed, and even then it took some tuning to get there.

Architecture

Both honeypots write JSON logs to disk. Promtail tails those files and ships them to Loki. Grafana queries Loki. All of it runs in Docker so the whole thing deploys with one command.

architecture
Cowrie (SSH :22)  +  Python HTTP (:80)
         |                    |
         +------+  JSON  +----+
                |
            Promtail
                |
              Loki
                |
            Grafana (:3000)

Before deploying, I moved real SSH access to port 443. Attackers almost never probe that port for SSH, and it stays open through most restrictive firewalls. That kept the box manageable while Cowrie owned port 22.

Setup

After provisioning the droplet and installing Docker, the deploy is just:

bash
git clone https://github.com/albierbi/honeypot.git
cd honeypot
cp .env.example .env
nano .env          # set Grafana password
mkdir -p logs/cowrie logs/http
docker compose up -d

Grafana comes up at http://VPS_IP:3000. The dashboard is provisioned automatically from the repo, no manual panel setup needed.

Important

Never run this on a machine you use for anything else. Cowrie is a sandbox but nothing is bulletproof. Dedicate a throwaway VPS to it.

Tuning Loki

This is the part no tutorial covers. The stack does not just work on 1 GB of RAM. A few things broke in ways that took a while to figure out.

The disappearing history problem

Loki's default compactor rewrites its index every 10 minutes or so. On a single-node setup this orphaned older chunks from the query path until the next restart, so dashboard history would silently vanish, then come back after a container restart. The fix was to basically disable the compactor:

loki/config.yml
compactor:
  compaction_interval: 8760h  # effectively disabled

OOM kills

Loki's default parallelism settings assume more RAM than a $6 droplet has. It kept getting killed mid-query, taking the dashboard down with it.

loki/config.yml
limits_config:
  max_query_parallelism: 2
  max_concurrent: 2
  max_query_length: 8760h   # allow 6-month dashboard panels

Log re-ingestion on restart

Promtail tracks which log lines it already shipped using a positions file. If that file isn't persisted across container restarts, it re-ingests everything from the start on every deploy, which means duplicated data and inflated numbers. Fixed with a Docker volume mount for the positions file.

All of this is already in the repo config. Writing it down here so I remember why it's there.

What attackers ran once they were "in"

Most sessions started with basic recon:

bash
uname -a
cat /proc/cpuinfo | grep name | wc -l
free -m
crontab -l

Then the most interesting single command, run 1,990 times word for word:

bash
cd ~ && rm -rf .ssh && mkdir .ssh && \
  echo "ssh-rsa AAAAB3Nz...mdrfckr" >> .ssh/authorized_keys && \
  chmod -R go= ~/.ssh
The Outlaw botnet

The mdrfckr tag on that SSH key is a known calling card of the Outlaw IoT botnet. Nearly 2,000 different compromised machines pasted the exact same command into the fake shell.

786 attackers ran this cleanup command first, which is bots killing other bots' malware before installing their own:

bash
rm -rf /tmp/secure.sh; rm -rf /tmp/auth.sh;
pkill -9 secure.sh; pkill -9 auth.sh;
echo > /etc/hosts.deny; pkill -9 sleep;

There's basically a turf war happening on thousands of abandoned servers at once, and the owners have no idea.

CVE-2017-9841

The phpunit path is a 9-year-old RCE vulnerability. It still got 910 attempts. Anything exposed on port 80 gets probed for it almost immediately.

Scanners try dozens of .env variants: /laravel/.env, /.env.old, /.env.save, /.env.backup. One leaked API key pays for scanning millions of IPs.

Botnets

The SSH client version field tells you what's actually on the other end:

connections / client version / meaning
245,400   SSH-2.0-Go              Custom Go scanner, dominant Chinese IoT botnet
 70,610   SSH-2.0-libssh_0.9.6   Another botnet flavor
  4,480   SSH-2.0-PuTTY_0.84     Actual humans on Windows
    324   SSH-2.0-Nmap-SSH2       Nmap scans

69% of all connections were the exact same Go scanner. The top single attacker, an IP out of Thailand (110.77.221.154), made 89,206 login attempts on its own over 75 days. Humans and researchers combined were a rounding error.

Malware payloads

Attackers tried to download binaries 2,810 times across 14 unique payloads. Sample names from the logs:

payload names
meow, meowarm64          -> likely Mirai variant
morte.x86, morte.mips,
morte.arc, morte.i468    -> cross-arch IoT malware
xnxnxnxnxnxnxn...aarch64 -> Gafgyt variant

The arm64, mips, arc, and aarch64 suffixes give it away. These bots were built for routers and IoT devices, not servers. They just tried the same playbook against my box anyway.

Where I used AI

I used Claude Code throughout this project, mainly for the parts that weren't the point of the exercise. It helped debug the Loki compactor issue described above, which took a while to track down. It also helped write the README from the raw log data and talked through Grafana panel design with me when I wasn't sure how to visualize something.

Deciding on the stack, provisioning the VPS, setting up the actual honeypots, moving SSH to a different port, and analyzing what the logs meant, that part was me. AI was a tool for the boring or fiddly bits, not a replacement for understanding what I was building.

Takeaways

What I learned
  • The internet probes anything exposed on port 22 within seconds, not minutes.
  • 69% of SSH traffic came from one botnet family. The threat landscape is more concentrated than I expected.
  • Credential stuffing is almost entirely automated: the same password lists, the same usernames, across thousands of IPs at once.
  • HTTP scanners hunt for .env files obsessively. One exposed key is worth scanning millions of servers for.
  • Loki on a 1 GB VPS needs real tuning. The defaults assume more RAM than you probably have.
  • Moving real SSH to port 443 worked exactly as expected. Zero noise on that port for 75 days.
